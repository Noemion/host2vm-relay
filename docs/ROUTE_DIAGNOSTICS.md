# 路由诊断

在“Clash 接入”的测试网址中填写目标地址，点击“检测路由是否生效”。检测使用已保存规则；编辑后请先保存。

| 检测结果 | 含义与处理 |
| --- | --- |
| 本地规则未命中 | 普通域名仅精确匹配。需要包含子域名时使用 `*.example.com`。域名解析后的 IP 规则是否匹配，以实际连接为准。 |
| 规则文件与保存内容不同 | 重新保存规则并检测应用情况；当前版本不会在断连时改写规则文件。 |
| Clash 未加载分流入口 | 重新生成并应用当前订阅的扩展脚本。 |
| 实际链路包含 Host2VMRelay 节点 | 已确认这次 TCP 请求选择了中继节点。网页内容和登录状态仍需另行验证。 |
| 实际链路为 DIRECT 或其他节点 | 查看同次请求的实际命中规则，检查规则遗漏、模式和策略组回退。 |
| TLS 证书失败 | 若收到证书，说明已到达 TLS 阶段。检查证书信任、域名和有效期，不要关闭验证。 |
| 没有捕获连接记录 | 不能判断链路成功，即使代理端口接受了请求。 |

诊断按自己的本地源端口、目标域名、目标端口及 TCP 类型匹配连接，不借用同域名的其他连接作为证据。控制接口错误、代理认证要求、超时和取消均显示未完成的检测阶段。

当前使用 Clash Verge 的本地命名管道，不启用新的网络控制端口。实际请求需要 HTTP 或混合代理端口；仅启用 SOCKS 端口时会说明无法实测。规则集条数不能证明内容完全一致。

本次检查不验证浏览器 TUN/DNS 接管、UDP、页面内容或登录。只发送域名和端口，HTTPS 执行正常的证书校验，不发送路径、查询参数、Cookie 或登录凭据。最长等待 25 秒，可随时取消。

## TUN 切换后等待恢复，但 SSH 仍连接

SSH 可通过 Host-only 网卡保持连接，而虚拟机的 NAT 网卡已经断链。先在虚拟机中检查 `ip -br link`、`ip route` 和内核日志；若 TUN 切换时 NAT 网卡出现 `NO-CARRIER`、默认路由消失，应先处理 VMware 网络状态传播，不能靠重启 Clash 或更快的 SSH 健康检查解决。

在“Clash 接入 → VMware NAT 稳定性”选择该虚拟机的 `.vmx` 文件，保存工作并完全关闭所有 VMware 虚拟机，然后应用修复。工具备份原文件，仅设置 `vmnat.linkStatePropagation.disable = "TRUE"`，不会关闭虚拟机，也不删除 VMware 锁文件。挂起状态不支持此操作。启动虚拟机后重新登录 VPN 并复测；配置已写入不等于运行中的虚拟机已经采用它。

如果 VPN 登录网关也属于内网后缀规则，在“VPN 网关 DNS 例外”保存网关的精确域名，再生成并应用脚本。此例外在内网 Fake-IP 规则之前返回真实 IP，不改变 TUN 设置，也不自动把所有虚拟机流量设为直连。已有客户端或 DNS 缓存仍可能保留旧地址，需再次验证实际解析与连接。

需要实测时，使用 TransportHarness 的显式现场测试（会关闭再开启当前 Clash TUN，不属于默认测试）：

```powershell
dotnet artifacts/transport/bin/Release/net8.0/TransportHarness.dll --live-tun-check https://internal.example/ 5 artifacts/checks/live-tun.json
```

测试先要求目标可达，每轮使用新连接和正常 TLS 校验，记录 TUN 开启请求耗时、开启完成后的 HTTP 响应耗时及总耗时。首次失败即停止并恢复 TUN 开启，避免持续打断 VPN；同时观察虚拟机网卡是否掉线。1 秒的 HTTP 恢复预算从 TUN 开启请求完成开始计算，TUN 自身创建设备的时间单独记录，不能混淆两者。
